A running log of decisions taken outside the spec, forced changes, tradeoffs, and anything else the maintainer needs to know. Newest entry first.

2026-07-29 — bitsandbytes 0.50 and torch 2.13 upstream drift

Reported problem. Two crashes from the training box: KeyError: 'percentile_clipping' at optimizers/adamw_8bit.py:30, and a failed import of check_serializing_named_tensor from torch._namedtensor_internals on torch 2.13.0.

What the audit actually found

The reported KeyError was one of four breakages, not one. Verified by extracting the bitsandbytes 0.50.0 wheel and reading the source rather than guessing:

Removed in bitsandbytes 0.50.0Where it broke
get_config() key percentile_clippingadamw_8bit.py:30 (the reported crash)
get_config() key block_wiseadamw_8bit.py:72 and :99 — the next two KeyErrors
functional.percentile_clippingadamw_8bit.py:31
functional.optimizer_update_8bit (non-blockwise)adamw_8bit.py:73

The positional order of optimizer_update_32bit and optimizer_update_8bit_blockwise did not change, so the Kahan summation logic itself needed no edit. That was checked argument by argument against the 0.50.0 source.

Decisions made that were not in the request

  • Kept the non-blockwise 8-bit branch instead of deleting it. The chosen approach was "support both 0.49.x and 0.50.x", so the branch stays reachable for users still on 0.49 where F.optimizer_update_8bit exists. On 0.50 the block_wise default of True means it is never entered, so the missing function is never touched.
  • Second elif reduced to a bare dtype check. elif state["state1"].dtype == torch.uint8 and config["block_wise"] became elif state["state1"].dtype == torch.uint8. It is logically equivalent once the preceding branch handles the non-blockwise case, and it avoids a second defensive config.get() for no benefit.
  • Inlined the torch helper rather than a try/except import. check_serializing_named_tensor is five lines with stable semantics. Importing it from a private module is what broke; a fallback import would leave the same fragility in place, so utils/reduction.py now defines it locally.
  • No pin added to requirements.txt. The version-adaptive fix works on both releases, and the project deliberately keeps dependencies unpinned.
  • Renamed the audit note. docs/note/submodule-signature-audit.md became docs/note/upstream-api-drift-audit.md because the rule now covers pip dependencies as well as submodules, and the old filename would have been misleading. Done with git mv to keep history; all three referring files were updated.
  • Guard script skips bitsandbytes instead of failing it. In tools/check_vendored_apis.py, a missing bitsandbytes is reported as [SKIP], so the torch half of the audit still runs (and still exits zero) on the CPU-only dev box where bitsandbytes is not part of the normal setup.

Tradeoffs weighed

  • Version-adaptive vs. following 0.50 exactly. Mirroring 0.50 would be cleaner and would delete two dead branches, but it breaks anyone on 0.49.x, and requirements.txt leaves bitsandbytes unpinned so that is a real population. Cost of the chosen path: two branches that are unreachable on modern bitsandbytes, kept alive by config.get() defaults.
  • Inlining vs. re-vendoring utils/reduction.py from torch 2.13. Re-vendoring would resync the whole file, but it is a large diff that needs real multi-process GPU testing to trust, and only one symbol was reported broken. Inlining is a five-line change; the guard script covers the risk that other symbols went missing too.
  • Test realism. The tests build AdamW8bitKahan via __new__ and stub bitsandbytes.functional, because the real update kernels need CUDA. That means they verify the config handling and the branch routing — the parts that actually broke — but not the numerics of the kernels themselves.

Things the maintainer needs to know

Not verifiable on the dev box. This machine runs torch 2.12.1+cpu, so the torch 2.13 removal could not be reproduced locally. utils/reduction.py depends on 14 other private torch symbols beyond the one that broke; all 14 were confirmed present on 2.12.1 but not on 2.13. Please run python tools/check_vendored_apis.py on the 2.13 training box and report any FAIL lines.

  • The dev venv changed. multiprocess and bitsandbytes==0.50.0 were installed into .venv so the fixes could be verified rather than assumed. bitsandbytes 0.50.0 ships a CPU-capable win_amd64 wheel and imports without a GPU, which is what made the audit checkable locally.
  • Tests. test/test_adamw_8bit.py (5 cases) covers the new and old config shapes, both 8-bit paths, and the Kahan compensation. Confirmed to reproduce the original KeyError: 'percentile_clipping' when the fix is reverted. Full suite: 31 passed.
  • Left out of the commit. An unrelated in-progress research note, docs/note/lumina2-vs-sd-scripts-training.md and its index line, was already uncommitted in the working tree. It was deliberately not included so this change stays atomic; it is still sitting in the working tree.
