Implementation notes

A running log of decisions taken outside the spec, forced changes, tradeoffs, and anything else the maintainer needs to know. Newest entry first.

2026-08-31 — Distillation: ZeRO option, refiner precision modes, and a crash-on-step-0 bug

Request. Add the real-ZeRO option that was offered at the end of the previous round (deepspeed.initialize + ZeRO-1 instead of DDP), then add mixed-precision / full-bf16 / fp16 support for the refiner.

The bug found on the way in

tools/distill_refiner.py could not complete a single training step. It used contextlib.nullcontext() at the no_sync call site and never imported contextlib. That expression is evaluated on the last micro batch of every step, and unconditionally when world_size == 1, so every run died with a NameError at step 0 in every configuration.

Why the suite did not catch it: every test in TestScriptStructure reads the file as a string and asserts on substrings, so the module was never imported. The distributed smoke test does import contextlib — but inside its own re-implementation of the accumulation loop, embedded as a string literal in the test file. The test had reimplemented the logic it was supposed to be testing, so it stayed green while the real code was broken. A 255 passed against tests shaped like that says less than it looks like it says.

Fixed, plus a test that imports the module rather than grepping it. The lesson is the generalisable part: source-substring assertions are cheap to write and cannot fail for the right reason. Several of the existing ones were rewritten to exercise behaviour instead.

ZeRO: added, but not made the default

The previous round’s arithmetic was correct and is why this is opt-in. ZeRO-1/2 shard optimizer state and gradients, so the ceiling on what they can save is the trainable share — 77.64M params, 1.24 GB, about 0.93 GB per GPU across four — while the ~5.20 GB of frozen bf16 LLM weights that dominate residency is exactly what those stages cannot touch. DDP remains the default. distributed_strategy = 'zero1' exists for the case where that 0.93 GB is the difference between starting and OOMing.

Launcher and strategy were separated properly: a DDPStrategy / DeepSpeedZeROStrategy pair behind one four-method interface, so the training loop has a single shape and deepspeed --num_gpus can drive DDP just as torchrun can drive ZeRO.

The dtype / precision confusion, which is worth stating loudly

[distill] dtype = 'bfloat16' has been in the config since this stage was written, and it reads like “this trains in bf16”. It does not, and never did. dtype applies only to the frozen modules — both LLMs, the LLMAdapter, the cross-attention probes, the probe queries. The trainable refiner is cast to fp32 in build_student unconditionally. So the config described the precision of everything except the thing being trained.

Rather than overload dtype, the refiner gets its own precision setting. Measured on identical data and seeds:

precisionRefiner paramsGrad dtypeAutocastScaler
fp32 (default)float32float32—no
bf16-mixedfloat32float32bfloat16no
fp16-mixedfloat32float32float16yes (DDP) / engine (ZeRO)
bf16-fullbfloat16bfloat16—no

Numbers behind the choice: the gradient reaching the refiner under bf16-full has cosine similarity 0.999994 with the fp32 gradient, at half the parameter storage. Separately, the bf16 hop through the frozen cross-attention that every mode already pays costs about 2.9e-03 relative gradient error — so the existing pipeline was already further from pure fp32 than bf16-full moves it.

Things the maintainer needs to know

  • The three precision axes are one object, not three settings. They are not independently valid: fp16 without a scaler underflows, a GradScaler on top of DeepSpeed’s own loss scaling scales twice, and autocast over bf16 parameters is a no-op that reads as if it were doing something. resolve_precision owns the whole mapping.
  • bf16-full means something different under ZeRO than under DDP. DeepSpeed’s bf16 mode keeps fp32 master weights in the optimizer, so it saves less than the DDP path and is numerically better. The asymmetry is deliberate and documented rather than papered over.
  • Precision is applied before the optimizer is constructed. AdamW sizes exp_avg and exp_avg_sq to each parameter’s dtype at construction, so casting afterwards leaves the optimizer holding state of the wrong dtype. There is a test asserting exp_avg comes out bf16 under bf16-full.
  • Do not add a bf16 section to the ZeRO config to “match” dtype. Under the default fp32 precision the DeepSpeed config deliberately carries no mixed-precision section; adding one casts the refiner and destroys the fp32 master weights the default mode depends on.
  • Do not set dtype = 'float16'. Gradients flow back through the frozen cross-attention at that dtype, and nothing scales them there.

Optimizer and LR schedule: reuse instead of reimplementation

Follow-up question from the maintainer, and a fair one: why does distillation hardcode torch.optim.AdamW and hand-roll a cosine schedule when train.py has nine optimizers and utils/lr_schedule.py exists? There was no principled reason. It was never wired up.

The optimizer turns out to matter more than the parallelism work above. Measured on the actual ContextRefiner (cap_feat_dim=2048, model_dim=1024, 6 layers), which is 77.64M parameters — matching the figure already in the docs:

Optimizer stateSizeNeeds
AdamW fp32 exp_avg + exp_avg_sq592 MB—
8-bit (uint8 state + per-block absmax)148 MBone GPU
ZeRO-1 saving, for comparison0.93 GB/GPUfour GPUs

So a single line of config frees 444 MB per GPU with no second GPU required — more per-GPU than the entire ZeRO effort reaches at this stage. Worth recording as a sequencing mistake: the ZeRO work was requested and delivered correctly, but if the underlying goal was VRAM, the cheaper answer was never surfaced first.

utils/optimizer_factory.py extracts only the name-to-class mapping out of train.py’s get_optimizer. Everything else there — parameter groups from the model, the weight-decay split keyed on p.original_name, gradient release with its pipeline-engine monkeypatching, the GenericOptim 2-d split — depends on the pipeline model and stayed put. train.py now calls the shared function; optim_type_lower is still defined for its two later uses.

Behaviour change, stated because it was promised not to happen. Moving to the shared LR scheduler is not bit-identical to the old hand-rolled cosine. Over 20000 steps with 500 warmup: 0.8% apart at step 5000, 4.6% at step 10000, and the shared one floors at eta_min = 1e-6 where the old decayed to ~0. Total area under the LR curve rises 3.44%. The optimizer side does keep exact backward compatibility — with no [optimizer] table it rebuilds the same AdamW from the same flat [distill] keys — but the scheduler side does not, and calling that "no behaviour change" would have been false.

A bug in the shared scheduler, left alone deliberately

create_lr_scheduler passes T_max=total_steps to CosineAnnealingLR, but under SequentialLR the warmup has already consumed warmup_steps of those. The cosine therefore advances only total_steps - warmup_steps of its period and never completes its anneal: with the distillation defaults it ends at 1.15e-6 instead of eta_min.

Not fixed. It affects every stage that goes through train.py, not just this one, so silently changing the LR schedule of every model in the repo while wiring up a distillation feature is the wrong trade. Flagged for a deliberate decision instead.

A config flaw the maintainer caught by reading

First version let lr appear in two places — flat under [distill] and inside the new [optimizer] table — and merged them. The merge was silently lossy: an [optimizer] table holding only type (exactly what someone switching to adamw8bit would write) inherited lr but fell back to torch’s defaults for betas and weight_decay, discarding the configured values with nothing printed. Measured: betas went from the configured (0.8, 0.95) to (0.9, 0.999) and weight_decay from 0.05 to 0.01.

Now refused rather than merged, following the "set exactly one" rule load_captions already applies to its three caption sources in the same file. The error names the offending keys. warmup_steps, lr_scheduler and max_grad_norm are exempt: they configure the schedule and clipping, not the optimizer.

Not verified

Stated plainly because the distinction matters more than the pass count.

8-bit optimizer under ZeRO is untested and warns at runtime. Confirmed by running that AdamW8bit state is genuinely quantised (uint8 state1/state2 plus fp32 qmap/absmax) and that it steps on CPU. Not confirmed: what happens when deepspeed.initialize replaces the optimizer’s param groups with its own flat fp32 partitions, leaving the quantisation blocks laid over partitions rather than whole parameters. Also worth knowing that the two save memory in the same place, so combining them buys well under the sum of their separate figures.

Verified by running: the DDP path across two real gloo ranks (three optimizer steps, grad norm 0.5894 → 0.5344 → 0.4902); all four precision modes end-to-end, each completing a full accumulate-and-step with finite gradients and weights that actually move; the generated DeepSpeed config parsed by DeepSpeed’s own DeepSpeedConfig; every DeepSpeed API called (get_global_grad_norm, backward, step, and all five initialize parameters) confirmed present in 0.19.6. 229 passed, 18 skipped.

Not verified: deepspeed.initialize has never actually run. The development container has no GPU and DeepSpeed hangs indefinitely on the CPU accelerator, with overlap_comm ruled out as the cause. The ZeRO tests use a fake engine, so they prove this code calls the right things in the right order — not that the real engine behaves as assumed. The load-bearing assumption is that engine.backward() applies the 1/N accumulation scaling itself; if that is wrong, the effective learning rate is off by exactly gradient_accumulation_steps and nothing reports it — the loss still falls, just at the wrong rate.

Cheapest check on real hardware: 200 steps at ddp and 200 at zero1, same seed, compare the loss curves. Also note that autocast is disabled on CPU by design, so the bf16-mixed and fp16-mixed numerics specifically have not been exercised either — on CPU they fall through to the fp32 path.

2026-08-31 — Caption corpus, tag dropout, multiline .txt captions

Request. A script that flattens every caption in a dataset.toml into one file, so distillation can be pointed at that file instead of the dataset. Plus tag dropout, and multi-line .txt sidecars.

A premise worth correcting first

The request was framed as recovering captions the pipeline drops: "if an image has multiple captions, the current flow only picks one." It does not. SizeBucketDataset.cache_latents expands every caption of every image into its own entry in iteration_order — an image with three captions is three training samples, and enumerate_captions already extended the whole list. With captions.json, nothing was ever being lost.

What is lost is narrower and real: a .txt sidecar is read as [f.read().strip()], so a file with three lines is one caption containing two newlines. That is the only place captions actually go missing.

So the corpus tool's value is not "recover dropped captions" — it is that distillation trains only the text frontend, and pointing it at a dataset.toml makes it walk every media file and open every tar purely to discover which captions exist. At three million images that is worth doing once. The corpus is a cache of that walk, not a second source of truth. Worth saying plainly, because a tool built on a wrong premise gets used for the wrong thing.

Decisions

  • The corpus is faithful, not preprocessed. Captions are written exactly as the dataset holds them, tag marker included, shuffling not baked in. One corpus then serves runs configured differently, and every epoch can draw a fresh variant. caption_prefix is the one exception — a fixed string with no random component, so it is applied at export.
  • Marker stripped at train time, not at export. Stripping it at export would be cleaner-looking and would destroy the only signal saying which captions are tag lists. A plain .txt corpus has nowhere to put a replacement flag, so that choice would have quietly made the tag/prose distinction unrepresentable in one of the three formats.
  • Dropout never empties a caption. An all-dropped caption is the empty string, which is the unconditional embedding — the trainer already mints those deliberately at UNCOND_FRACTION. Silently producing more would shift the conditioning ratio with no config change to explain it. With two tags at rate 0.5 that is a 1-in-4 event, not a corner case. At least one tag always survives.
  • multiline_captions is opt-in. Turning it on changes how many training samples every existing dataset with wrapped .txt files produces. That is a silent retraining-scope change for models unrelated to this branch, so it defaults off and needs --regenerate_cache, matching how cache_shuffle_num already behaves.
  • Distillation augments per sample; the diffusion stages cannot. The diffusion stages bake cache_shuffle_num variants into the embedding cache, because the embedding is computed once. Distillation re-embeds every step, so freezing a fixed variant set there would be a pure loss. It reads its settings from the dataset.toml's top level when that is the source, so a run matches the diffusion stages without restating them — top-level keys only, since a flat batch of captions has no directory to attach an override to.
  • Case-insensitive marker matching, requested mid-implementation. A marker is a hand-written annotation spread over millions of files; "Special:", "special:" and "SPECIAL: " have to mean the same thing. Only the first len(marker) characters are casefolded — this runs per sample and captions are long. The body is stripped afterwards, so "SPECIAL: a, b" does not train as " a, b" and tokenize differently from its neighbours for no reason.

A test failure that was worth listening to

Seven exporter tests failed with ModuleNotFoundError: No module named 'comfy_aimdo'. The tests run the script as a subprocess, which does not get conftest.py's stub. The easy fix was to stub it in the subprocess too.

The failure was pointing at something real: a tool that reads text files was importing torch, DeepSpeed and ComfyUI, because enumerate_captions happened to live in utils/dataset.py. Caption resolution needs nothing but the standard library. It moved to utils/captions.py, re-exported from utils/dataset.py so no existing caller changed. The tests went from 52s to 0.5s — that number is the import cost, paid on every invocation of the exporter, for nothing.

The QA pass that mattered most

The reviewer's first finding was mine, it was a blocker, and it had nothing to do with captions. Extracting the caption code by text range swallowed bucket_suffix, dedup_and_sort and seed_from_hash, which happened to sit between shuffle_captions and _map_and_cache. utils/dataset.py calls all three at twelve sites. Every training run, for every model in the repo, died at dataset construction. The copies that landed in utils/captions.py were broken too — that module imports neither numpy, hashlib nor ROUND_DECIMAL_DIGITS.

And 182 tests passed. The module still imported cleanly, and not one test in this repository had ever constructed a DirectoryDataset, ARBucketDataset or SizeBucketDataset. A green suite was not evidence of anything here. test/test_dataset_smoke.py now builds those objects against real images, and walks utils/dataset.py's AST asserting every global name it loads actually resolves — which catches the class of bug, not just these three names. Reverting the fix makes it fail at collection.

The reviewer also confirmed, by differential test against the pre-branch implementation, that shuffle_captions at its defaults is byte-identical including the RNG call sequence; that fuzzing 3000 adversarial strings through all three corpus formats round-trips cleanly; and that the casefold() slicing concern does not materialise, because the same index partitions the caption on both sides.

What the frozen-dropout question exposed

Asked whether tag dropout does anything when embeddings are cached, the honest answer turned out to be "sometimes not". Augmentation is baked into the embedding cache, so tag_dropout_rate with cache_shuffle_num = 0 produces exactly one draw, frozen forever — permanent tag deletion wearing an augmentation's name. It now warns.

That question also produced the better feature. caption_sampling = "random_per_epoch" gives one sample per image with the caption drawn on each access, instead of one sample per caption. All the embeddings are already cached and already indexable, so the draw is just an index — nothing extra to cache. And because the draw ranges over every cached variant, shuffling and dropout become real augmentation again with cached embeddings, which is what the frozen-draw problem needed.

One constraint fell out of reading the other models rather than assuming: per-sample augmentation is applied only when no text embeddings were cached (SDXL always; Cosmos with cache_text_embeddings = false). HiDream caches CLIP and T5 but tokenizes Llama3 from the live caption — re-augmenting there would make the cached embedding and the live text describe different captions. The check is not self.text_embedding_datasets, which excludes it correctly without naming any model.

Not verified. Still no training run, no multi-GPU run, no image. The corpus round-trip, the augmentation semantics and the exporter are covered by 56 CPU tests including newline/backslash/unicode round-trips through all three formats, but no corpus has been built from a real multi-million-image dataset, and the claim that reading a corpus is meaningfully faster than walking a dataset is reasoning about I/O, not a measurement.

A third QA pass, and the worst bug on the branch

The first finding was mine, it was a blocker, and it had nothing to do with the feature being reviewed. ContextRefiner.init_weights() was written to run after __init__, so it set only the ten values that differ from PyTorch's defaults. But the pipeline builds the refiner under init_empty_weights() and materialises every parameter with torch.empty. The other eighteen kept whatever the allocator last held — measured up to 1e32, sometimes NaN.

The reviewer saw NaN in k_proj and NaN gradients on step 1. The same script here produced garbage that stayed finite through four training steps, because the zeroed residual branches mask it until training moves them off zero. That difference is the point: the behaviour depended on allocator residue, so it differed between machines and between runs. A comment in cosmos_predict2.py asserted init_weights() "overwrites it". It did not.

2026-08-30 — Anima Refiner: replacing Anima's LLMAdapter text frontend

Request. Add an architecture that swaps Anima's LLMAdapter for the cap_embedder + bidirectional refiner blocks that Lumina 2 and Z-Image use, so any Transformers LLM (target: Qwen3.5-2B-Base) can drive the DiT. New model type anima_refiner; cosmos_predict2 and anima must be untouched.

Why the adapter exists at all

Worth recording, because it explains the whole design. In ComfyUI Anima is literally class Anima(MiniTrainDIT) — a Cosmos-Predict2 DiT whose only addition is the adapter. Cosmos-Predict2 feeds old-T5 encoder output straight into cross-attention with no adapter, so the adapter is a retrofit letting a Qwen3 LLM drive a T5-native DiT.

The mismatch it papers over is not dimensional: old T5-XXL has d_model = 1024 and Qwen3-0.6B has hidden_size = 1024. They already agree. A six-layer cross-attention module with a 32128-entry embedding table was built anyway, which is the evidence that the gap is representational — bidirectional encoder vs causal decoder, span corruption vs next-token, sentencepiece vs BPE.

Findings that changed the design

FindingConsequence
Qwen3.5 interleaves linear and full attention (full_attention_interval = 4), full-attention layers at 3/7/11/15/19/23 hidden_states[-2], Lumina 2's convention, lands after a linear-attention layer. Default is -1 here.
Linear-attention layers are recurrences with no attention matrix They cannot be made bidirectional by flipping a mask, so the refiner's bidirectional blocks are load-bearing, not decoration.
Qwen3.5-2B and Qwen3.5-2B-Base have byte-identical config.json No architecture change needed for Base; only the tokenizer differs (eos <|endoftext|> vs <|im_end|>). Verified by fetching both.
Teacher and student features are indexed by different tokenizers A position-wise distillation MSE runs without error while comparing unrelated slots. The loss is measured at the cross-attention output instead, which is a weighted sum over text positions and therefore invariant to indexing.

Mistakes made in the first version, and what fixed them

Recorded honestly, because four of them were regressions in code shared with other models.

Shape derived from config instead of from the weights. load_diffusion_model loads with if name not in state_dict: continue, so a checkpoint holding more refiner layers than n_refiner_layers asked for silently lost the surplus. Measured: a 4-layer refiner loaded under the default of 6 dropped 24 tensors with no warning. Now the layer count and input dimension come from the weights, and a config that contradicts them raises.

cache_name discarded the VAE latents. A config key was added to invalidate stale text embeddings when the text encoder changed. It worked by changing the pipeline's name, which is the root of the whole cache tree — so switching text encoder also threw away latents, by far the more expensive half, for a component that had not changed. Replaced by a text-encoder identity mixed into the text embedding fingerprint only. anima_refiner now also shares anima's cache directory deliberately, so latents cached by an anima run are reused as is.

Three smaller leaks into shared code, all now gated on the model type: base_lr and max_text_length were read unconditionally, giving anima and cosmos_predict2 config keys nobody asked for; and the vision-language branch of the llm_path directory loader changed how anima would load a VLM.

One near-miss caught during implementation rather than after: the text-encoder identity was first appended to new_fingerprint_args unconditionally. Hasher.hash([i]) and Hasher.hash([i, '']) differ, so that would have invalidated the text embedding cache of every model in the repo. Extra fingerprint args are now only appended when non-empty, and the old fingerprint was verified byte-for-byte.

Decisions made that were not in the request

  • OPLoRA excludes the refiner. OPLoRA projects a low-rank update away from the top-k singular subspace of the pretrained base weight. A newly built refiner has no pretrained weights to protect, and two of its six Linear layers per block are zero-initialised — where, as measured, the SVD does not fail or produce NaN but returns an arbitrary orthonormal basis. Projecting against that costs the adapter rank directions for nothing. Implemented as a per-model oplora_exclude_names, empty everywhere else.
  • Distillation reads dataset.toml. It originally took a bespoke caption format while every other mode used the repo's. Now it goes through utils.dataset.enumerate_captions(), which mirrors DirectoryDataset's resolution rules exactly. Images are enumerated to find their captions but never opened.
  • context_refiner_path wins over the checkpoint, loudly. Both orderings are defensible; silence is not, so it warns naming both files every time.
  • Stage numbering removed. stage1/stage2 implied a pipeline the code does not enforce — every mode loads identically and can run in any order. The configs are named for what they train instead.

DefectWhy it survived the author's own review

The distillation auxiliary loss used a mask-normalised mean while the primary term is measured through an attention softmax. Padding changes the softmax denominator but not a masked mean, so the two terms disagreed about what a "position" is. A plausible-looking helper. Replaced with padded_mean(x, mask, length), which normalises by the same padded length the attention does.
LoRA targeted RefinerBlock, so cap_embedder — which hangs off ContextRefiner, not off any block — was never adapted. The one projection that has to move for a new text encoder to land was frozen in every adapter run. get_target_modules matches a class name and then walks only that module's own nn.Linears. Target changed to ContextRefiner; a test now asserts a cap_embedder LoRA parameter exists.
train_context_refiner wrote its refiner beside the adapter in the same save directory. Two .safetensors in one directory makes load_adapter_weights raise on resume. Only ever exercised as a fresh run. The refiner now goes to a context_refiner/ subdirectory.
Docs said n_refiner_layers is "ignored" when the checkpoint carries a refiner. The code raises on a conflict — deliberately, after the silent-weight-drop bug earlier on this branch. The doc was written before that fix and never revisited. Docs corrected, and the key removed from the configs that point at refiner-bearing checkpoints.
A blanket rename of the Unsloth references also rewrote the README line that documents the Unsloth option itself. Self-inflicted, by sed over a whole file instead of a located line. Reverted.
--device cpu in the sampler was broken twice over: an unconditional .to('cuda') on the VAE statistics, and a float32 timestep fed to a bf16 model. The CPU path was added for testability and then never run end to end on CPU. Both fixed; it now runs.
A fractional num_repeats crashed caption enumeration, and a config['probe'] subscript assumed an optional key was present. Two ordinary omissions. Repeats now expand as int(len(captions) * num_repeats) with wraparound indexing.

The twelfth finding — that implementation-notes.html is a stray artifact this branch introduced — is wrong. The file predates the branch (commit a0efffa) and is the document you are reading. Recorded here rather than quietly dropped, because a QA pass being right eleven times out of twelve is exactly the pattern that makes the twelfth easy to accept without checking.

What the two passes have in common is worth naming: not one of these fourteen defects was a wrong algorithm. They were an import order, a prefix, a mask, a dict key, a class name, a directory layout, and a doc that had drifted from its code. All of them sit in the seams between two pieces that were each individually correct.

Not verified

Development happened on a CPU-only box with no model weights. Everything is covered by CPU tests — including a real optimisation loop over the layer stack to_layers() builds, and sampling checked against a synthetic velocity field where the exact answer is known — but no training run, no multi-GPU run and no image was ever produced. Multi-GPU is covered indirectly by asserting the invariants pipeline parallelism depends on: constant tensor shapes across micro batches, and every layer boundary being a valid split point. Real DeepSpeed execution still needs deepspeed --num_gpus=2 --module test.debug_deepspeed_init.

Also unproven: sampling quality. tools/sample_anima_refiner.py is verified for integration math and shape handling, not for producing good images.

See docs/anima_refiner/README.md for the architecture and docs/anima_refiner/lessons.md for the rules these mistakes turned into.

2026-07-29 — bitsandbytes 0.50 and torch 2.13 upstream drift

Reported problem. Two crashes from the training box: KeyError: 'percentile_clipping' at optimizers/adamw_8bit.py:30, and a failed import of check_serializing_named_tensor from torch._namedtensor_internals on torch 2.13.0.

What the audit actually found

The reported KeyError was one of four breakages, not one. Verified by extracting the bitsandbytes 0.50.0 wheel and reading the source rather than guessing:

Removed in bitsandbytes 0.50.0Where it broke
get_config() key percentile_clippingadamw_8bit.py:30 (the reported crash)
get_config() key block_wiseadamw_8bit.py:72 and :99 — the next two KeyErrors
functional.percentile_clippingadamw_8bit.py:31
functional.optimizer_update_8bit (non-blockwise)adamw_8bit.py:73

The positional order of optimizer_update_32bit and optimizer_update_8bit_blockwise did not change, so the Kahan summation logic itself needed no edit. That was checked argument by argument against the 0.50.0 source.

Decisions made that were not in the request

  • Kept the non-blockwise 8-bit branch instead of deleting it. The chosen approach was "support both 0.49.x and 0.50.x", so the branch stays reachable for users still on 0.49 where F.optimizer_update_8bit exists. On 0.50 the block_wise default of True means it is never entered, so the missing function is never touched.
  • Second elif reduced to a bare dtype check. elif state["state1"].dtype == torch.uint8 and config["block_wise"] became elif state["state1"].dtype == torch.uint8. It is logically equivalent once the preceding branch handles the non-blockwise case, and it avoids a second defensive config.get() for no benefit.
  • Inlined the torch helper rather than a try/except import. check_serializing_named_tensor is five lines with stable semantics. Importing it from a private module is what broke; a fallback import would leave the same fragility in place, so utils/reduction.py now defines it locally.
  • No pin added to requirements.txt. The version-adaptive fix works on both releases, and the project deliberately keeps dependencies unpinned.
  • Renamed the audit note. docs/note/submodule-signature-audit.md became docs/note/upstream-api-drift-audit.md because the rule now covers pip dependencies as well as submodules, and the old filename would have been misleading. Done with git mv to keep history; all three referring files were updated.
  • Guard script skips bitsandbytes instead of failing it. In tools/check_vendored_apis.py, a missing bitsandbytes is reported as [SKIP], so the torch half of the audit still runs (and still exits zero) on the CPU-only dev box where bitsandbytes is not part of the normal setup.

Tradeoffs weighed

  • Version-adaptive vs. following 0.50 exactly. Mirroring 0.50 would be cleaner and would delete two dead branches, but it breaks anyone on 0.49.x, and requirements.txt leaves bitsandbytes unpinned so that is a real population. Cost of the chosen path: two branches that are unreachable on modern bitsandbytes, kept alive by config.get() defaults.
  • Inlining vs. re-vendoring utils/reduction.py from torch 2.13. Re-vendoring would resync the whole file, but it is a large diff that needs real multi-process GPU testing to trust, and only one symbol was reported broken. Inlining is a five-line change; the guard script covers the risk that other symbols went missing too.
  • Test realism. The tests build AdamW8bitKahan via __new__ and stub bitsandbytes.functional, because the real update kernels need CUDA. That means they verify the config handling and the branch routing — the parts that actually broke — but not the numerics of the kernels themselves.
