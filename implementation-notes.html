Implementation notes

A running log of decisions taken outside the spec, forced changes, tradeoffs, and anything else the maintainer needs to know. Newest entry first.

2026-08-30 — Anima Refiner: replacing Anima's LLMAdapter text frontend

Request. Add an architecture that swaps Anima's LLMAdapter for the cap_embedder + bidirectional refiner blocks that Lumina 2 and Z-Image use, so any Transformers LLM (target: Qwen3.5-2B-Base) can drive the DiT. New model type anima_refiner; cosmos_predict2 and anima must be untouched.

Why the adapter exists at all

Worth recording, because it explains the whole design. In ComfyUI Anima is literally class Anima(MiniTrainDIT) — a Cosmos-Predict2 DiT whose only addition is the adapter. Cosmos-Predict2 feeds old-T5 encoder output straight into cross-attention with no adapter, so the adapter is a retrofit letting a Qwen3 LLM drive a T5-native DiT.

The mismatch it papers over is not dimensional: old T5-XXL has d_model = 1024 and Qwen3-0.6B has hidden_size = 1024. They already agree. A six-layer cross-attention module with a 32128-entry embedding table was built anyway, which is the evidence that the gap is representational — bidirectional encoder vs causal decoder, span corruption vs next-token, sentencepiece vs BPE.

Findings that changed the design

FindingConsequence
Qwen3.5 interleaves linear and full attention (full_attention_interval = 4), full-attention layers at 3/7/11/15/19/23 hidden_states[-2], Lumina 2's convention, lands after a linear-attention layer. Default is -1 here.
Linear-attention layers are recurrences with no attention matrix They cannot be made bidirectional by flipping a mask, so the refiner's bidirectional blocks are load-bearing, not decoration.
Qwen3.5-2B and Qwen3.5-2B-Base have byte-identical config.json No architecture change needed for Base; only the tokenizer differs (eos <|endoftext|> vs <|im_end|>). Verified by fetching both.
Teacher and student features are indexed by different tokenizers A position-wise distillation MSE runs without error while comparing unrelated slots. The loss is measured at the cross-attention output instead, which is a weighted sum over text positions and therefore invariant to indexing.

Mistakes made in the first version, and what fixed them

Recorded honestly, because four of them were regressions in code shared with other models.

Shape derived from config instead of from the weights. load_diffusion_model loads with if name not in state_dict: continue, so a checkpoint holding more refiner layers than n_refiner_layers asked for silently lost the surplus. Measured: a 4-layer refiner loaded under the default of 6 dropped 24 tensors with no warning. Now the layer count and input dimension come from the weights, and a config that contradicts them raises.

cache_name discarded the VAE latents. A config key was added to invalidate stale text embeddings when the text encoder changed. It worked by changing the pipeline's name, which is the root of the whole cache tree — so switching text encoder also threw away latents, by far the more expensive half, for a component that had not changed. Replaced by a text-encoder identity mixed into the text embedding fingerprint only. anima_refiner now also shares anima's cache directory deliberately, so latents cached by an anima run are reused as is.

Three smaller leaks into shared code, all now gated on the model type: base_lr and max_text_length were read unconditionally, giving anima and cosmos_predict2 config keys nobody asked for; and the vision-language branch of the llm_path directory loader changed how anima would load a VLM.

One near-miss caught during implementation rather than after: the text-encoder identity was first appended to new_fingerprint_args unconditionally. Hasher.hash([i]) and Hasher.hash([i, '']) differ, so that would have invalidated the text embedding cache of every model in the repo. Extra fingerprint args are now only appended when non-empty, and the old fingerprint was verified byte-for-byte.

Decisions made that were not in the request

  • OPLoRA excludes the refiner. OPLoRA projects a low-rank update away from the top-k singular subspace of the pretrained base weight. A newly built refiner has no pretrained weights to protect, and two of its six Linear layers per block are zero-initialised — where, as measured, the SVD does not fail or produce NaN but returns an arbitrary orthonormal basis. Projecting against that costs the adapter rank directions for nothing. Implemented as a per-model oplora_exclude_names, empty everywhere else.
  • Distillation reads dataset.toml. It originally took a bespoke caption format while every other mode used the repo's. Now it goes through utils.dataset.enumerate_captions(), which mirrors DirectoryDataset's resolution rules exactly. Images are enumerated to find their captions but never opened.
  • context_refiner_path wins over the checkpoint, loudly. Both orderings are defensible; silence is not, so it warns naming both files every time.
  • Stage numbering removed. stage1/stage2 implied a pipeline the code does not enforce — every mode loads identically and can run in any order. The configs are named for what they train instead.

Not verified

Development happened on a CPU-only box with no model weights. Everything is covered by CPU tests — including a real optimisation loop over the layer stack to_layers() builds, and sampling checked against a synthetic velocity field where the exact answer is known — but no training run, no multi-GPU run and no image was ever produced. Multi-GPU is covered indirectly by asserting the invariants pipeline parallelism depends on: constant tensor shapes across micro batches, and every layer boundary being a valid split point. Real DeepSpeed execution still needs deepspeed --num_gpus=2 --module test.debug_deepspeed_init.

Also unproven: sampling quality. tools/sample_anima_refiner.py is verified for integration math and shape handling, not for producing good images.

See docs/anima_refiner.md for the architecture and docs/anima_refiner_lessons.md for the rules these mistakes turned into.

2026-07-29 — bitsandbytes 0.50 and torch 2.13 upstream drift

Reported problem. Two crashes from the training box: KeyError: 'percentile_clipping' at optimizers/adamw_8bit.py:30, and a failed import of check_serializing_named_tensor from torch._namedtensor_internals on torch 2.13.0.

What the audit actually found

The reported KeyError was one of four breakages, not one. Verified by extracting the bitsandbytes 0.50.0 wheel and reading the source rather than guessing:

Removed in bitsandbytes 0.50.0Where it broke
get_config() key percentile_clippingadamw_8bit.py:30 (the reported crash)
get_config() key block_wiseadamw_8bit.py:72 and :99 — the next two KeyErrors
functional.percentile_clippingadamw_8bit.py:31
functional.optimizer_update_8bit (non-blockwise)adamw_8bit.py:73

The positional order of optimizer_update_32bit and optimizer_update_8bit_blockwise did not change, so the Kahan summation logic itself needed no edit. That was checked argument by argument against the 0.50.0 source.

Decisions made that were not in the request

  • Kept the non-blockwise 8-bit branch instead of deleting it. The chosen approach was "support both 0.49.x and 0.50.x", so the branch stays reachable for users still on 0.49 where F.optimizer_update_8bit exists. On 0.50 the block_wise default of True means it is never entered, so the missing function is never touched.
  • Second elif reduced to a bare dtype check. elif state["state1"].dtype == torch.uint8 and config["block_wise"] became elif state["state1"].dtype == torch.uint8. It is logically equivalent once the preceding branch handles the non-blockwise case, and it avoids a second defensive config.get() for no benefit.
  • Inlined the torch helper rather than a try/except import. check_serializing_named_tensor is five lines with stable semantics. Importing it from a private module is what broke; a fallback import would leave the same fragility in place, so utils/reduction.py now defines it locally.
  • No pin added to requirements.txt. The version-adaptive fix works on both releases, and the project deliberately keeps dependencies unpinned.
  • Renamed the audit note. docs/note/submodule-signature-audit.md became docs/note/upstream-api-drift-audit.md because the rule now covers pip dependencies as well as submodules, and the old filename would have been misleading. Done with git mv to keep history; all three referring files were updated.
  • Guard script skips bitsandbytes instead of failing it. In tools/check_vendored_apis.py, a missing bitsandbytes is reported as [SKIP], so the torch half of the audit still runs (and still exits zero) on the CPU-only dev box where bitsandbytes is not part of the normal setup.

Tradeoffs weighed

  • Version-adaptive vs. following 0.50 exactly. Mirroring 0.50 would be cleaner and would delete two dead branches, but it breaks anyone on 0.49.x, and requirements.txt leaves bitsandbytes unpinned so that is a real population. Cost of the chosen path: two branches that are unreachable on modern bitsandbytes, kept alive by config.get() defaults.
  • Inlining vs. re-vendoring utils/reduction.py from torch 2.13. Re-vendoring would resync the whole file, but it is a large diff that needs real multi-process GPU testing to trust, and only one symbol was reported broken. Inlining is a five-line change; the guard script covers the risk that other symbols went missing too.
  • Test realism. The tests build AdamW8bitKahan via __new__ and stub bitsandbytes.functional, because the real update kernels need CUDA. That means they verify the config handling and the branch routing — the parts that actually broke — but not the numerics of the kernels themselves.

Things the maintainer needs to know

Not verifiable on the dev box. This machine runs torch 2.12.1+cpu, so the torch 2.13 removal could not be reproduced locally. utils/reduction.py depends on 14 other private torch symbols beyond the one that broke; all 14 were confirmed present on 2.12.1 but not on 2.13. Please run python tools/check_vendored_apis.py on the 2.13 training box and report any FAIL lines.

  • The dev venv changed. multiprocess and bitsandbytes==0.50.0 were installed into .venv so the fixes could be verified rather than assumed. bitsandbytes 0.50.0 ships a CPU-capable win_amd64 wheel and imports without a GPU, which is what made the audit checkable locally.
  • Tests. test/test_adamw_8bit.py (5 cases) covers the new and old config shapes, both 8-bit paths, and the Kahan compensation. Confirmed to reproduce the original KeyError: 'percentile_clipping' when the fix is reverted. Full suite: 31 passed.
  • Left out of the commit. An unrelated in-progress research note, docs/note/lumina2-vs-sd-scripts-training.md and its index line, was already uncommitted in the working tree. It was deliberately not included so this change stays atomic; it is still sitting in the working tree.
